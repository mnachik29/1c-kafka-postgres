# Архитектура

```
 ┌──────────────┐  OData (HTTP, JSON)  ┌─────────────────────┐   1c.ownership_forms.v1   ┌──────────────────┐   upsert   ┌────────────┐
 │ 1С:Предпр.   │ ───────────────────▶ │ integration-service │ ───────────────────────▶  │ consumer-service │ ─────────▶ │ PostgreSQL │
 │ (Apache +    │  $filter по          │ (Java 21, CLI +     │   1c.counterparties.v1    │ (Java 21,        │  1 транз.  │            │
 │  wsap24)     │  ДатаИзменения       │  /health)           │   key = Ref_Key           │  group pg-sink)  │  на пакет  │            │
 └──────────────┘                      └─────────────────────┘                           └────────┬─────────┘            └────────────┘
                                         state: /data/sync-state.json                             │ невалидные / ошибки данных
                                         (метка по справочнику)                                   ▼

```

## Integration-service

* **Источник** — стандартный OData-интерфейс 1С (вариант А из задания). Своего кода на стороне 1С нет,
  кроме метки `ДатаИзменения` в модуле объекта.
* **Режимы:** `sync --mode full` читает всё, `sync --mode incremental` — только
  `ДатаИзменения >= метка − SYNC_OVERLAP_SECONDS`. Метка — максимальная `ДатаИзменения` среди уже
  опубликованных записей. Она берётся из данных 1С, а не из часов сервиса, поэтому расхождение часов не влияет.
  Метка сдвигается только после `producer.flush()`, когда Kafka подтвердила все сообщения.
* **Пагинация:** `$top/$skip` с сортировкой `ДатаИзменения, Ref_Key`, поэтому порядок стабилен.
* **Порядок:** сначала формы собственности, потом контрагенты.
* **Producer:** `acks=all`, `enable.idempotence=true`. Ключ — `Ref_Key`: все версии объекта попадают в
  одну партицию и сохраняют порядок.
* **event_id** детерминированный: UUIDv3 от `(event_type, id, DataVersion, deleted)`. Одна и та же версия
  объекта всегда даёт один и тот же event_id.
* **Ошибки 1С:** retry с экспоненциальной задержкой для сетевых ошибок и 5xx. 400/401/403/404 не повторяются
  (неверный запрос, нет прав, объект не опубликован). Всё логируется структурированно, при сбое код выхода 1.
* **Защита от параллельных запусков:** файловая блокировка `sync.lock`.

## Kafka

* Топики `1c.ownership_forms.v1` и `1c.counterparties.v1`, по 3 партиции, `cleanup.policy=compact`:
  в топике всегда остаётся последняя версия каждого объекта, и новый потребитель может построить
  полную копию справочника.
* DLQ: `1c.ownership_forms.dlq`, `1c.counterparties.dlq`, retention 14 дней. В заголовках — причина
  ошибки, исходный топик, партиция и offset.
* `auto.create.topics.enable=false`: топики создаёт только `kafka-init`.

## Consumer-service

* Consumer group `pg-sink`, `enable.auto.commit=false`, пакет до 500 сообщений за `poll()`.
* **At-least-once + идемпотентность:** offset коммитится только после `COMMIT` в PostgreSQL. Если
  сообщение придёт повторно, upsert ничего не изменит.
* **Upsert:** `INSERT … ON CONFLICT (id) DO UPDATE … WHERE`, где
  * `EXCLUDED.source_updated_at >= t.source_updated_at` — более старая версия не затрёт новую;
  * `(поля) IS DISTINCT FROM (EXCLUDED.поля)` — строка не обновляется, если ничего не поменялось
    (повторная полная синхронизация не трогает `imported_at`).
* **Внешний ключ:** формы и контрагенты читаются из разных топиков, поэтому контрагент может прийти
  раньше своей формы. Тогда создаётся строка-заглушка (`placeholder = true`), и настоящее событие формы
  её перезаписывает. Внутри одного пакета формы всегда пишутся раньше контрагентов.
* **Ошибки:**
  * невалидный JSON или схема → сразу в DLQ;
  * временные ошибки БД (SQLSTATE 08/40/53/57, нет соединения) → retry с backoff. Если не помогло —
    исключение, consumer пересоздаётся и перечитывает пакет с последнего закоммиченного offset.
    Сообщения не теряются и в DLQ не уходят;
  * ошибки данных (нарушение ограничений и т.п.) → пакет переписывается по одному, «плохие»
    сообщения уходят в DLQ, остальные сохраняются.
* Миграции схемы — Flyway (`migrations/`) при старте.

## PostgreSQL

`ownership_forms(id TEXT PK)`, `counterparties(id UUID PK, ownership_form_id → ownership_forms)`.
Технические поля: `source_updated_at`, `source_data_version`, `last_event_id`, `created_at` (первый импорт),
`imported_at` (последний импорт, который изменил строку), `placeholder`.

`ownership_forms.id` — это `Ref_Key` формы собственности из 1С (GUID в виде текста), а не мнемоника
вроде `ooo` из примера в задании. Это стабильный идентификатор, он не меняется при переименовании.
Тип колонки оставлен `TEXT`, как в схеме из задания.

## Наблюдаемость

* JSON-логи (logstash-logback-encoder), бизнес-поля вынесены в отдельные ключи (`entity`, `topic`,
  `offset`, `sql_state`, …).
* `GET :8081/health` — integration-service и доступность 1С; `GET :8082/health` — PostgreSQL и consumer
  loop (503, если БД недоступна или `poll()` не вызывался больше 60 с).
* `GET /metrics` — счётчики в формате Prometheus.
